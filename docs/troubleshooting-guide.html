Local Environment & Tooling

Before AWS was even involved.

01Homebrew doesn't have Terraform anymoretooling
Symptom
Warning: No available formula with the name "terraform"

Where: brew install terraform on any modern Mac.

Why: HashiCorp relicensed Terraform (BSL), so Homebrew removed it from its core repository.

Fix
brew tap hashicorp/tap
brew install hashicorp/tap/terraform
When a famous package "disappears" from a package manager, check for a vendor-owned tap/repo before assuming breakage.
02JDK cask install failed — needs a password I can't givetooling
Symptom
sudo: a terminal is required to read the password

Where: brew install --cask temurin@17 from a non-interactive session (needed a JVM to run PySpark tests locally).

Why: Casks run macOS installers that require sudo; formulas install into Homebrew's own prefix and don't.

Fix
brew install openjdk@17   # formula, no sudo — then point JAVA_HOME at it
Prefer formulas over casks in automation; casks assume a human at the keyboard.
03Local package named mcp/ shadowed the MCP SDKtooling
Symptom

Would have been an import loop: from mcp.server import Server inside mcp/server.py imports itself, not the SDK.

Where: The repo's MCP server directory vs the installed mcp pip package.

Fix
git mv mcp mcp_server   # never name a local package after a dependency
Python resolves your local directory first. Naming a package after its own dependency is a time bomb.
04The MCP SDK's API had completely changed (v2.0)tooling
Symptom

Code written against the documented low-level API (@server.list_tools(), stdio_server) didn't match the installed SDK — those symbols had moved or gone.

Fix

Inspected the installed package directly (dir(), inspect.signature) and rewrote against the new MCPServer decorator API (@server.tool()), verified by listing tools programmatically before shipping.

In fast-moving ecosystems, the installed package is the documentation. Interrogate it before writing against memory or old docs.
05Spark tests asserted different times on different machinestooling
Symptom
assert datetime(2026,3,1,7,0) == datetime(2026,3,1,12,0)   # off by exactly the local UTC offset

Where: Local PySpark tests asserting timestamp equality.

Why: PySpark converts timestamps to Python datetimes using the driver's local timezone on collect().

Fix
# conftest.py, before the JVM starts
os.environ["TZ"] = "UTC"; time.tzset()
Pin the test process to UTC. Any timestamp test that passes only in one timezone is already broken.
06Spark's least() silently eats NULLs — a real logic bugspark
Symptom

A customer's first transaction (no prior location → distance should be NULL) came back as 20,015 km — the exact antipodal maximum — flagging everyone's first purchase as impossible travel.

Where: The haversine helper's NaN guard: F.least(a, F.lit(1.0)).

Why: SQL's least() skips NULLs instead of propagating them, so least(NULL, 1.0) = 1.0 → asin(1) → half the Earth's circumference.

Fix
capped = F.when(a.isNotNull(), F.least(a, F.lit(1.0)))   # NULL stays NULL
least/greatest ignore NULLs by SQL standard. Guard explicitly whenever NULL means "unknown" rather than "zero". A local unit test caught this — that's why the transforms are pure functions.

Terraform & Infrastructure-as-Code

Found by terraform validate and first applies.

07S3 Vectors resources don't export .arnterraform
Symptom
Error: Unsupported attribute — This object has no ... "arn"
Fix

The attributes are service-prefixed: vector_bucket_arn and index_arn. Confirmed by dumping the provider schema (terraform providers schema -json) instead of guessing.

For brand-new AWS services, the provider schema is the source of truth — grep it, don't assume conventions.
08Firehose rejects an SSE block when reading from Kinesisterraform
Symptom
"server_side_encryption": conflicts with kinesis_source_configuration

Why: With a Kinesis source, records arrive already encrypted; Firehose's own SSE setting is meaningless and the provider enforces that.

Fix

Delete the block, leave a comment explaining why it's absent so nobody "helpfully" re-adds it.

When two settings conflict, the fix often isn't choosing one — it's understanding which one was never applicable.
09Terraform has floor(), not round()terraform
Symptom
Error: There is no function named "round".
Fix

floor() / ceil(). HCL's function library is small and worth skimming once.

HCL is not a general-purpose language; verify functions exist before leaning on them.
10Brand-new S3 bucket 404'd its own uploads mid-applyterraform
Symptom
Error: reading S3 Object (…/bronze_job.py): couldn't find resource

Where: The very first apply, uploading Glue scripts seconds after creating the bucket.

Why: A new bucket's name takes a minute to propagate through AWS DNS; the provider's read-back races it.

Fix

Nothing to change — re-run terraform plan && apply. Terraform reconciles and finishes the stragglers (13 resources on the second pass).

First-apply failures on brand-new buckets are usually propagation, not configuration. Re-plan before debugging.
11"Saved plan is stale" — plan files are single-useterraform
Symptom
Error: Saved plan is stale — state was changed by another operation after the plan was created

Where: Running apply tfplan a second time, or after any other plan/apply touched state.

Fix

Regenerate: terraform plan -out=tfplan then apply the fresh file. If the first apply actually succeeded, the new plan simply says "No changes".

A plan file is a one-shot snapshot pinned to a state serial. Stale ≠ broken; it's a consistency guarantee doing its job.
12Replacing a resource orphaned its dependent in stateterraform
Symptom
ResourceNotFoundException: DataSource with id GAJKPQHZZM in knowledgeBase CHB9ICDAZG is not found

Where: Replacing the S3 Vectors index forced the Knowledge Base to be recreated; its old data source died with it, but Terraform still held the corpse in state and tried to update it against the new KB.

Fix
terraform state rm 'module.bedrock[0].aws_bedrockagent_data_source.policies'
terraform plan && apply   # recreates it fresh
When a parent is replaced and the provider doesn't cascade correctly, state rm the dead child and let Terraform recreate it. State surgery is a normal tool, not a hack.
13stream-down by flag left tfvars saying "on"terraform
Symptom

A later routine plan unexpectedly wanted to recreate the Kinesis stream (+$29/mo).

Why: make stream-down used -var enable_stream=false — a one-shot override; the recorded default in terraform.tfvars still said true, and the next plain plan reasserted it.

Fix

Caught it in plan review and pinned the tfvars to match reality before applying.

Command-line var overrides don't persist. If a toggle matters for cost, make the file reflect the truth — and always read the plan summary line.

Glue & Spark — the seven-run gauntlet

Local tests passed; the cloud had opinions. Each failure moved one stage further.

14Run 1–2 · "Cannot modify the value of a static config"spark
Symptom
AnalysisException: Cannot modify the value of a static config: spark.sql.extensions

Where: Every Glue job — configuring Iceberg with spark.conf.set() after getting the session.

Why: Session extensions and catalog implementations are static configs — they must exist before the SparkSession is born.

Fix
conf = SparkConf()
for k, v in iceberg_conf().items(): conf.set(k, v)
sc = SparkContext.getOrCreate(conf)      # config BEFORE context
Spark configs come in two castes: static (pre-session) and runtime. Extensions, catalogs, and classpath-adjacent settings are always static.
15Run 3 · The quality gate was denied publishing its own metricsspark
Symptom
User …/fraud-lake-glue-role is not authorized to perform: cloudwatch:PutMetricData

Where: Glue Data Quality's built-in CloudWatch publishing.

Why: My IAM policy scoped PutMetricData to fraud-lake/* namespaces — but Glue DQ publishes to the AWS-owned namespace Glue Data Quality.

Fix
values = ["fraud-lake/*", "Glue Data Quality"]   # in the namespace condition
Tight IAM scoping is right — but managed features publish under their own namespaces/paths. Budget one allow-list entry for the service itself.
16Run 4 · process_rows returns a collection, not a framespark
Symptom
AttributeError: 'DynamicFrameCollection' object has no attribute 'toDF'

Why: EvaluateDataQuality().process_rows returns two frames — per-rule verdicts (ruleOutcomes) and per-row annotations — wrapped in a collection.

Fix
rule_outcomes = SelectFromCollection.apply(dfc=outcomes, key="ruleOutcomes")
results = rule_outcomes.toDF()...
Glue's transform APIs often return collections. When an AWS API surprises you, the runtime error names the real type — read it literally.
17Run 7 · F.nullif works locally, dies on Gluespark
Symptom
AnalysisException: Invalid call to dataType on unresolved object

Where: Gold job's loss-rate division guard — passed 40 local Spark tests, failed on Glue 5.

Why: Glue's Spark fork rejects nullif() over unresolved columns even though stock PySpark 3.5 accepts it.

Fix
F.when(F.col("total") > 0, 100.0 * F.col("loss") / F.col("total"))  # NULL otherwise
Glue ≈ Spark, not =. Prefer boring primitives (when/otherwise) over exotic functions in code that must run on managed forks. Getting the true stack trace from CloudWatch (not the truncated console error) was what cracked this.

Data Quality (DQDL) — a language with sharp edges

Six semantics traps in one small rule language.

18Run 5 · Hand-rolled freshness: 0% of fresh rows "passed"dqdl
Symptom
ColumnValues "transaction_timestamp" > (now() - 3 hours) → "0.00 % of rows passed"

Why: The now()-arithmetic expression doesn't evaluate the way it reads on timestamp columns. The data was provably 90 minutes old.

Fix

First switched to DataFreshness… which exposed issue 19. Final form is issue 19's CustomSql.

If a DQ rule fails at exactly 0% or 100% on data you know is mixed, suspect the rule's semantics before the data.
19DataFreshness is per-row — yesterday's good data "goes stale"dqdl
Symptom

(Caught in audit before it fired.) DataFreshness <= 3 hours evaluates every row of the whole table — so any run more than 3 hours after the first batch would fail forever on history.

Fix
CustomSql "SELECT COUNT(*) FROM primary
           WHERE transaction_timestamp > current_timestamp() - INTERVAL 3 HOURS" > 0

Liveness = "does at least one recent row exist", not "is every row young".

Pin down whether a rule is per-row or per-dataset before trusting it. Freshness is a property of the newest row.
20Run 6 · One boolean-vs-string rule poisoned all 15 rulesdqdl
Symptom
14 of 15 rules "failed", every one carrying the same error:
DATATYPE_MISMATCH … (is_high_velocity IN (true, false)) … ["BOOLEAN","STRING","STRING"]

Why: ColumnValues "is_high_velocity" in ["true","false"] compared a BOOLEAN column to strings — a Spark type error that took the whole evaluation query down with it.

Fix

Replaced with IsComplete (existence is the meaningful check; the true/false mix lives on the dashboard).

DQ rules compile into one big query — one type-broken rule fails everything. When every rule fails identically, look for the one malformed rule, not fifteen data problems.
21DQDL between excludes its own boundariesdqdl
Symptom

fraud_signal_count between 0 and 4 fails every row with 0 signals — the most common value. Same trap waited on rates of exactly 0% or 100%.

Fix
between -1 and 5          # the inclusive 0..4
between -0.001 and 100.001  # for percentages
DQDL's between is exclusive. Nudge bounds outward whenever the boundary value is legitimate.
22NULLs count as failures even with a threshold that "should" cover themdqdl
Symptom
ColumnValues "geo_distance_from_prior_km" >= 0 with threshold >= 0.60
→ "Value: NULL does not meet the constraint requirement!"

Why: Every customer's first transaction has NULL distance by design — a large share of a young table. NULLs fail ColumnValues, and the young-table NULL share overwhelmed a threshold calibrated for a mature one.

Fix

Recalibrated the threshold for the table's actual life stage (0.60), documented that it tightens as history accumulates.

Rules that are correct for a mature table can be wrong for a young one. Calibrate thresholds to the data you have, not the data you'll have.
23ReferentialIntegrity can't see catalog tables — and the cold-start paradoxdqdl
Symptom

(Caught in audit.) Two stacked problems: ① DQDL's ReferentialIntegrity resolves its reference against datasets wired into the evaluator call — a catalog path in the rule string errors out. ② The referenced merchant_dim is created by the silver job, which runs after the bronze gate: on the first-ever run the table can't exist.

Fix
# ① same check, ordinary Spark, where the Iceberg catalog already exists:
CustomSql "SELECT COUNT(*) FROM primary p
           LEFT ANTI JOIN glue_catalog.fraud_silver.merchant_dim d
           ON p.merchant_id = d.merchant_id" = 0
# ② quality job detects the missing dim and drops this one rule on the first run only
Bootstrapping order matters: a gate must not depend on an artifact produced downstream of itself — unless it knows how to cold-start. And CustomSql is the escape hatch for anything DQDL's built-ins can't express.

Bedrock & the AI Layer

24The Model Access page is gone; Anthropic wants a form anywaybedrock
Symptom
ResourceNotFoundException: Model use case details have not been submitted for this account.

Where: First Claude invocation. Meanwhile Amazon's own Titan model worked instantly — that asymmetry was the clue.

Why: AWS retired per-model enablement (models now auto-enable on first invoke), but Anthropic's provider terms still require a one-time use-case form.

Fix

Bedrock console → Playgrounds → pick a Claude model → submit the use-case form (a GitHub profile URL works as "company website" for individuals). Active within ~15 minutes, once per account, ever.

Platform gates and provider gates are different layers. When one model works and another doesn't, suspect provider terms, not your IAM.
25Knowledge Base ingestion failed 3 of 4 documentsbedrock
Symptom
Invalid record: Filterable metadata must have at most 2048 bytes (S3Vectors, 400)

Why: S3 Vectors caps filterable metadata at 2,048 bytes/vector, and Bedrock stores each chunk's full text in metadata. I declared the wrong key non-filterable, so real chunks blew the cap. The tell: the only "success" was a 28-byte placeholder file.

Fix
non_filterable_metadata_keys = ["AMAZON_BEDROCK_TEXT",
  "AMAZON_BEDROCK_TEXT_CHUNK", "AMAZON_BEDROCK_METADATA"]  # cover all variants

Result: 3/3 documents indexed, retrieval scoring 0.87 on the first query.

When most items fail and one tiny one succeeds, the size of the survivor is the diagnosis. Also: exclude junk placeholders from any prefix a knowledge base ingests.

Lake Formation — five lessons in one afternoon

The most gotcha-dense service in the project. Each error was the security model teaching itself.

26IAM admin ≠ Lake Formation adminlakeformation
Symptom
AccessDeniedException: Resource does not exist or requester is not authorized (GrantPermissions)

Why: LF keeps its own administrator registry, separate from IAM. Even AdministratorAccess can't manage grants until registered as a data lake administrator.

Fix
resource "aws_lakeformation_data_lake_settings" "main" {
  admins = [caller_arn]
  # + explicitly preserve IAM_ALLOWED_PRINCIPALS create-defaults
}
IAM decides who can call APIs; Lake Formation separately decides who governs data. Register before granting — and preserve create-defaults so enabling LF can't silently break table creation.
27Column exclusions need wildcard=true — and per-table listslakeformation
Symptom
"table_with_columns.0.wildcard": one of column_names, wildcard must be specified

Plus: a shared exclusion list would have failed anyway — LF rejects excluding a column the table doesn't have, and the two gold tables have different columns.

Fix

wildcard = true alongside excluded_column_names ("all columns except these"), with a separate exclusion list per table.

Exclusions are exclusions from a wildcard. And schema-coupled security config must be maintained per table, not shared.
28Personas denied S3 — hybrid mode needs opt-inslakeformation
Symptom
PERMISSION_DENIED: … not authorized to perform: s3:GetObject on …/gold/…/metadata/…

Why: The persona roles have no direct S3 access by design — they rely on LF credential vending. But the location was registered in hybrid mode, which only vends for principals explicitly opted in.

Fix

Registered the location in standard mode (vends for any LF-permitted principal), and registered the gold/ prefix where the data actually lives. Also: Athena needs s3:GetBucketLocation on the results bucket — a one-line IAM add.

Hybrid vs standard registration decides who gets vended credentials. And register the prefix your data actually lives under, not a notional one.
29Column filters silently shadowed by the account defaultlakeformation
Symptom

No error at all — the worst kind. Effective permissions are a union, and the default IAMAllowedPrincipals = ALL grant on every table would have given the analyst full columns despite the careful exclusion grant.

Fix
# grant the pipeline + agent roles explicitly FIRST, then per table:
aws lakeformation revoke-permissions \
  --principal DataLakePrincipalIdentifier=IAM_ALLOWED_PRINCIPALS \
  --permissions ALL --resource '{"Table":{...}}'
LF's grandfathered default makes every IAM principal super-user until revoked per table. Order matters: explicit grants for everything that must keep working, then revoke the default.
30The revoke cut off the admin itself — and the AI agent with itlakeformation
Symptom
Insufficient permissions … Principal does not have any privilege on specified resource

Where: The admin's own Athena queries — and therefore the agent's query_lakehouse tool — right after revoking the default.

Why: Data lake administrators hold grant power, not implicit data access. Admins govern; access is always explicit.

Fix

An explicit SELECT grant to the admin identity on the gold tables. Agent answering again in 11.5 s.

The final and best lesson of the day: in a properly governed lake, nobody — not even the administrator — reads data without an explicit grant. If your governance change breaks you too, it's probably working.

Account & Console

31Budget blocked by an accidental empty "action"console
Symptom
Review the errors below and try again — Select IAM role (required)

Why: Budget actions (auto-applying lockdown policies) are an advanced feature needing an execution role; an empty one was added by mis-click. Email alerts need none of it.

Fix

Click Remove on the action; save. Alerts-only is the right shape for a personal project.

In AWS consoles, the advanced optional feature is often one mis-click away from blocking the basic flow. Remove what you didn't mean to add rather than satisfying its requirements.
32IAM admin gets "Access denied" all over Billingconsole
Symptom

Every cost tile in Billing red with "Access denied" — while holding AdministratorAccess.

Why: Billing has a separate root-only gate: "IAM user and role access to Billing information" is off by default.

Fix

Log in as root once → Account settings → activate IAM access to billing. (Root logs in with the account email, not a username.)

Billing is special-cased outside IAM until root opens it. Do it on day one, then put root away with MFA.

Process & Operations

33Deleting bad rows downstream didn't stickprocess
Symptom

Deleted 146 unknown-merchant rows from bronze; the very next run re-imported all 146 and the gate failed again identically.

Why: Bronze re-derives from the raw zone every run — and the poisoned objects were still sitting in raw. Raw is immutable-by-design; downstream deletes can't survive a re-derive.

Fix

Remediate upstream first: delete the 4 poison objects from raw (identified precisely by their Firehose timestamp window), then the Iceberg DELETE FROM in bronze, then re-run → green.

In a medallion architecture, fixes flow the same direction as data. Cleaning a derived layer while the source stays dirty just schedules the same incident again.
34"It failed again!" — no, that's yesterday's reportprocess
Symptom

Three separate times, an old failure report or a previous execution's status was mistaken for the current run's result — causing phantom "regressions".

Why: Failure reports in S3 and the Step Functions execution list are history. They accumulate; nothing about them says "not current".

Fix

Ritual: before diagnosing anything, match the report's timestamp / execution's start time against when you actually ran. Named executions help (s3-… = auto-trigger, UUID = manual).

Every artifact you read during an incident needs a freshness check first. The most convincing wrong evidence is real evidence from the wrong time.
